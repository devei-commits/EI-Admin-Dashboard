  A) STANDALONE MODULE LAYOUT (StandaloneModuleLayout)
     These modules render WITHOUT the admin sidebar — they have their own
     internal navigation:
       /pis/*             → PIS (Product Info Sheet) module
       /treasury/*        → Treasury module
       /procurement       → Procurement module
       /warehouse/*       → Warehouse module
       /planning/*        → Planning module
       /production        → Production module
       /fulfillment       → Fulfillment module
       /client-hub        → Client Hub module

  B) ADMIN SIDEBAR LAYOUT
     All other routes render inside the main admin shell with Sidebar:
       /                  → Dashboard
       /role-management   → Role Management
       /user-management   → User Management
       /catalogue-management
       /active-ingredients / /customization-catalog
       /enquiry-management / /doctor-appointments / /contact-enquiry

  A catch-all route (*) redirects to Dashboard.

5. AUTHENTICATION & SESSION MANAGEMENT
================================================================================

  Flow:
    1. User submits email + password → POST /api/v1/auth/login
    2a. If MFA enabled:  backend returns OTP_SENT → user enters OTP
                         → POST /api/v1/otp/verifyotp
    2b. If no MFA:       backend returns user + JWT token
    3. Token stored in   localStorage key: "ei_admin_token"
    4. User object stored in localStorage key: "eisthetic_auth_user"
    5. On app load, existing token is verified via GET /api/v1/auth/me

  Session Expiry Detection:
    - apiClient.ts detects 401/403 responses or "SESSION_EXPIRED" code
    - Dispatches custom DOM event: "ei:session-expired"
    - AuthContext + SessionExpiredNotifier listen and clear state / redirect

  AuthUser shape:
    { id, email, name, roleId, roleName, roleLevel, allowedModules, loginTime }

  Token lifecycle:
    - setAuthToken()  → stores to localStorage
    - getAuthToken()  → reads from localStorage
    - clearAuthToken() → removes from localStorage
    - All API requests attach:  Authorization: Bearer <token>

6. API CLIENT
================================================================================

  File: src/lib/apiClient.ts

  Central fetch wrapper used by all service files. Provides:
    api.get<T>(path)
    api.post<T>(path, data)
    api.put<T>(path, data)
    api.patch<T>(path, data)
    api.delete<T>(path)

  Base URL resolution:
    - Development: empty string → Vite dev proxy forwards /api → localhost:3000
    - Production:  VITE_API_BASE_URL env var (set to backend origin)

  Features:
    - Automatically attaches Bearer token header
    - Handles FormData (skips Content-Type header so browser sets boundary)
    - On 4xx/5xx: parses JSON/text body, extracts server error message
    - On session expiry: clears token + dispatches "ei:session-expired" event
    - 204 No Content → returns undefined
    - Returns parsed JSON for all other success responses


================================================================================
7. SERVER STATE MANAGEMENT (TanStack Query)
================================================================================

  File: src/lib/queryClient.ts

  QueryClient configuration:
    staleTime          : 30 seconds
    gcTime (cacheTime) : 30 minutes
    retry              : up to 3 times (skips 404s and client errors)
    retryDelay         : exponential backoff (max 30 seconds)
    refetchOnWindowFocus: false
    refetchOnReconnect  : false
    refetchOnMount     : 'always'  (picks up backend cache invalidations)

  Query Key Registry (queryKeys):
    orders, order(id), reviewOrders, users, roles, products, enquiries,
    dashboard, analytics, warehouseLocations, warehouseInventory

  Data flow:
    Component → custom hook (e.g. useGRN) → service function → apiClient
             ↓
    TanStack Query caches response, handles loading/error states


================================================================================
8. ROLE-BASED ACCESS CONTROL (RBAC)
================================================================================

  Hook: src/hooks/usePermissions.ts
  Guard: src/components/ProtectedModuleRoute.tsx

  Permission levels:
    1. MODULE level    → can user access this module at all?
    2. SUB-MODULE level → can user view/create/edit/delete/approve/export?
    3. COLUMN level    → can user view/edit a specific data column?

  Admin bypass:
    Users with roleName "admin" / "super admin" OR roleLevel "admin"
    get full access to everything — no backend fetch needed.

  Non-admin flow:
    On login, role ID from /me is used to fetch
    GET /api/v1/roles/:roleId → returns permissions JSON
    This is parsed into a RolePermissions object used throughout the app.

  ProtectedModuleRoute usage:
    <ProtectedModuleRoute moduleId="inventory" subModuleId="raw-materials">
      <RawMaterialForm />
    </ProtectedModuleRoute>

  allowedModules (from /me):
    Fallback when role permissions haven't loaded yet.
    '*' means full access.

  Code Splitting (manualChunks):

  Vercel:
    vercel.json → rewrites for SPA routing

13. KEY ARCHITECTURAL PATTERNS
================================================================================

  1. SERVICE LAYER
     All backend calls go through dedicated service files (src/services/).
     Components never call apiClient directly — they call service functions.
     Service functions return typed results or throw on error.

  2. TANSTACK QUERY FOR SERVER STATE
     All async data is managed by TanStack Query via custom hooks.
     Components read from query cache; mutations invalidate relevant keys.
     This eliminates manual loading/error state management.

  3. LAZY LOADING FOR PERFORMANCE
     Every page component is lazy-loaded. The Vite build produces separate
     JS chunks per page + vendor chunks. Users only download what they visit.

  4. DUAL LAYOUT ARCHITECTURE
     Complex operational modules (Procurement, Warehouse, Planning, etc.)
     render in StandaloneModuleLayout with their own internal nav.
     Simpler admin modules render inside the shared Admin Sidebar layout.

  5. RBAC VIA HOOK + ROUTE GUARD
     usePermissions() is the single source of truth for what a user can do.
     ProtectedModuleRoute wraps routes to block unauthorized access at the
     router level. Individual components use usePermissions() for fine-grained
     action/column-level control.

  6. EVENT-DRIVEN SESSION EXPIRY
     Session expiry is handled via a custom DOM event ("ei:session-expired")
     rather than prop drilling. Any part of the app can detect and react to
     an expired session without needing to be aware of sibling components.

  7. ERROR BOUNDARIES
     ErrorBoundary components wrap all route subtrees. If a page throws during
     render, the boundary catches it and shows a fallback UI instead of a
     white screen crash.

  8. CENTRALIZED CONSTANTS & TYPES
     Route-to-module mappings, quality spec defaults, status maps, and order
     fulfillment constants live in src/constants/ so they are single-sourced.
     TypeScript types in src/types/ are shared across services and components.
